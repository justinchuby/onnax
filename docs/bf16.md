# BF16 LoRA: explicit compute and surrogate derivatives

This experiment executes the [LoRA model](lora.md) with BF16 matrix operands and
results, FP32 nonlinearities/loss, and FP32 master parameters, local derivatives and
Adam state. Run it with ONNX's **CPU ReferenceEvaluator** to check numerical behavior
and exported graphs.

```bash
uv sync --group dev --group training
uv run python -m examples.lora.bf16 --output-dir bf16_models
```

## What is computed

Write $Q$ for FP32 → BF16 → FP32 rounding. Each of the four matrix products in $\hat
Y=\tanh(XW+XAB/4)C$ becomes

$$
M(A,B)=Q\bigl(Q(A)Q(B)\bigr).
$$

The local ONNX function casts both inputs to BF16, calls a **BF16 MatMul**, then casts
the result to FP32. Tests check that the optimized graph contains four matrix nodes with
BF16 input and output types. Stored W/C and A/B masters remain FP32. The nonlinearity,
residual, mean squared loss and local backward matrix products remain FP32. The
reference backend uses NumPy matrix arithmetic internally.

The example-only `lower_matmuls` helper replaces rank-two FP32 matrix calls with this
explicit local function. Importing `examples.lora.bf16_rules` globally registers its
JVP/VJP with the existing decorators. Builtin rules are unchanged; users still call
`onnax.grad(model, inputs=["lora.A", "lora.B"], output="loss")`. The registered rule
applies to this local function. Direct differentiation of raw BF16 paths is currently
unsupported.

## Straight-through derivatives

The local function uses identity straight-through derivatives at each rounding boundary:

$$
\dot M=\dot A\,Q(B)+Q(A)\,\dot B,
\qquad
\bar A=\bar M\,Q(B)^\mathsf{T},\quad
\bar B=Q(A)^\mathsf{T}\bar M.
$$

These formulas use rounded primal operands and FP32 matrix products and gradient fan-in.
Tests show that a small literal finite difference inside a BF16 rounding interval is
zero while this declared derivative is nonzero. They separately verify JVP/VJP agreement
and central finite differences of a **smooth local surrogate** that holds rounding
offsets fixed at the parameter point.

This prototype supports first-order gradients. A subsequent JVP can encounter
unsupported BF16 rounding paths in the backward graph. Use FP32/FP64 graphs for
[scientific-computing products](fitting.md).

## Independent checks and FP32 accuracy baseline

An independent NumPy implementation rounds finite FP32 values by their bit
representation, without calling ONNX execution operators or registered rules. Tests
check nearest-even ties, both signs, signed zeros and subnormals against an actual dtype
cast. Independent analytic backpropagation uses the specified straight-through
convention. At each of 200 updates, forward, loss and both gradients are compared at
identical parameters, and parameters/loss are compared with a separately evolving,
flattened NumPy Adam implementation. Comparisons use `rtol=1e-4, atol=1e-6`.

BF16 rounding boundaries make trajectories sensitive to tiny FP32 ordering differences.
The oracle therefore pins the same numerical evaluation contract: Tanh's slope uses
$4e^{-2|z|}/(1+e^{-2|z|})^2$ to avoid subtraction cancellation; Adam's second-moment
contribution multiplies $(1-\beta_2)g$ before multiplying by $g$ again. The reference
maintains its own parameters and optimizer state. Smooth-surrogate finite differences
check the derivative formula.

The CLI also trains a separate all-FP32 graph for 200 updates using the same reference
backend, data, initial parameters and Adam. A recorded development run:

| Quantity | Value |
| --- | ---: |
| BF16 initial validation MSE | 0.01622 |
| BF16 final validation MSE | 0.000002706 |
| FP32-trained final validation MSE | 0.000000004597 |
| FP32 forward at final BF16-trained parameters, validation MSE | 0.000001463 |
| Maximum BF16/FP32 prediction difference at those same parameters | 0.00803 |

The BF16 fit has a larger final error than the FP32 baseline. The same-parameter
comparison measures forward quantization error, while the separately trained baseline
also captures differences in the update trajectory. Regression checks require a 50%
training/validation loss decrease and validation RMSE below 0.01 on this synthetic
dataset.

## Portable exports and external master state

`loss.onnx` and `gradient.onnx` retain the local function. `gradient.inlined.onnx` and
`gradient.optimized.onnx` contain standard-domain nodes for execution on a runtime with
BF16 operator support. Every graph passes full ONNX checker; function, inlined and
optimized graphs are compared after loading with dynamic batch sizes 1, 7 and 128.

ONNXScript optimizes a copy. Constant-fold size limits are set to zero for this
experiment to preserve frozen FP32 master initializers. Other simplification/CSE
rewrites still run. Original source and base artifacts are checked unchanged. ORT graph
optimization is not used.

The versioned `interface.json` records parameter-to-gradient names, shapes,
master/gradient dtypes, loss reduction, frozen master hashes and the derivative
convention. `adapter.npz` contains FP32 A/B masters. `checkpoint.npz` additionally
stores the Adam step and FP32 first/second moments; loading it reproduces the next
parameter/state update exactly. The example handles serialization and regenerates
compute copies from the masters.

## Measurements and next steps

Separate worker processes measure the exported BF16 and FP32 graphs on the same CPU
ReferenceEvaluator backend. Each runs 10 warmups and 100 measured gradient and external
Adam updates, reporting model load/session creation, median/P95 stages, process RSS,
versions and thread environment. The parent pins common BLAS/OpenMP thread environment
variables to one before worker imports. CPU calls are synchronous; feed/output handling
and reference casts are included.

The BF16 graph uses a rank-two local VJP; the FP32 graph uses the builtin general VJP.
The report records their node counts alongside timings. Peak process RSS includes
imports, allocator and runtime state. The [recorded
report](https://github.com/justinchuby/onnax/blob/main/examples/measurements/bf16-lora-apple-arm64.json)
contains the accuracy and timing results.

Next steps are native backend execution, device bindings, broader precision transforms
and device memory/transfer measurements. On the recorded machine, the CPU ORT probe
reports a missing BF16 MatMul kernel.

The graph uses the standard [ONNX Cast](https://onnx.ai/onnx/operators/onnx__Cast.html)
and [MatMul](https://onnx.ai/onnx/operators/onnx__MatMul.html) operators.
