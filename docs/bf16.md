# BF16 LoRA: explicit compute and surrogate derivatives

This experiment executes the [LoRA model](lora.md) with BF16 matrix operands and
results, FP32 nonlinearities/loss, and FP32 master parameters, local derivatives
and Adam state. It uses ONNX's **CPU ReferenceEvaluator**, not a native BF16
accelerator. It establishes a numerical and export contract; native CPU ORT still
fails the separate BF16 MatMul capability probe on the recorded machine.

```bash
uv sync --group dev --group training
uv run python -m examples.lora.bf16 --output-dir bf16_models
```

## What is computed

Write $Q$ for FP32 → BF16 → FP32 rounding. Each of the four matrix products in
$\hat Y=\tanh(XW+XAB/4)C$ becomes

$$
M(A,B)=Q\bigl(Q(A)Q(B)\bigr).
$$

The local ONNX function casts both inputs to BF16, calls a **BF16 MatMul**, then
casts the result to FP32. This is not an FP32 matrix graph relabeled as BF16.
The optimized exported graph is checked to contain four matrix nodes with actual
BF16 input and output types. Stored W/C and A/B masters remain FP32. The
nonlinearity, residual, mean squared loss and local backward matrix products
remain FP32. The reference backend may use wider internal arithmetic for its
matrix implementation; no native BF16 hardware instruction or universal kernel
accumulation dtype is inferred from a tensor type.

The example-only `lower_matmuls` helper replaces rank-two FP32 matrix calls with
this explicit local function. Importing `examples.lora.bf16_rules` globally
registers its JVP/VJP with the existing decorators. Builtin rules are unchanged;
users still call `onnax.grad(model, inputs=["lora.A", "lora.B"], output="loss")`.
This is an opt-in function with a declared derivative, not generic raw BF16
active-path support. Direct differentiation of an inlined BF16 path remains
unsupported. No mandatory per-call rules object or training-framework API is added.

## The derivative is an explicit convention

Rounding is piecewise constant and discontinuous. Its literal derivative cannot
provide the training gradient used here. The local function declares identity
straight-through derivatives for each rounding boundary:

$$
\dot M=\dot A\,Q(B)+Q(A)\,\dot B,
\qquad
\bar A=\bar M\,Q(B)^\mathsf{T},\quad
\bar B=Q(A)^\mathsf{T}\bar M.
$$

These matrix products and all gradient fan-in are FP32. The rounded primal
operands, rather than unrounded masters, appear in these formulas. Tests show
that a small literal finite difference inside a BF16 rounding interval is zero
while this declared derivative is nonzero. They separately verify JVP/VJP
agreement and central finite differences of a **smooth local surrogate** that
holds rounding offsets fixed at the parameter point. No agreement with literal
finite differences of a quantized staircase is claimed.

This prototype validates first-order gradients. Higher derivatives and vmap of
this mixed-precision local function are not promised. In particular, generated
backward operand-rounding paths can trigger the existing BF16 active-path
rejection in a subsequent JVP. Use the existing FP32/FP64 graphs for the
[scientific-computing products](fitting.md).

## Independent checks and FP32 accuracy baseline

An independent NumPy implementation rounds finite FP32 values by their bit
representation, without calling ONNX execution operators or registered
rules. Tests check nearest-even ties, both signs, signed zeros and subnormals
against an actual dtype cast. Independent analytic backpropagation uses the
specified straight-through convention. At each of 200 updates, forward, loss
and both gradients are compared at identical parameters, and parameters/loss
are compared with a separately evolving, flattened NumPy Adam implementation.
The existing `rtol=1e-4, atol=1e-6` is unchanged.

BF16 rounding boundaries make trajectories sensitive to tiny FP32 ordering
differences. The oracle therefore pins the same numerical evaluation contract:
Tanh's slope uses $4e^{-2|z|}/(1+e^{-2|z|})^2$ to avoid subtraction cancellation;
Adam's second-moment contribution multiplies $(1-\beta_2)g$ before multiplying
by $g$ again. The oracle is independent code and an independently evolving
state, not a reference reset to the graph's parameters. The smooth-surrogate
finite-difference checks independently validate the derivative formula.

The CLI also trains a separate all-FP32 graph for 200 updates using the same
reference backend, data, initial parameters and Adam. A recorded development run:

| Quantity | Value |
| --- | ---: |
| BF16 initial validation MSE | 0.01622 |
| BF16 final validation MSE | 0.000002706 |
| FP32-trained final validation MSE | 0.000000004597 |
| FP32 forward at final BF16-trained parameters, validation MSE | 0.000001463 |
| Maximum BF16/FP32 prediction difference at those same parameters | 0.00803 |

The BF16 fit improves substantially but retains a larger error than the FP32
baseline. Both forward quantization and the resulting update trajectory matter;
loss decrease alone is not evidence of equal accuracy. Regression checks require
at least a 50% training/validation loss decrease and validation RMSE below 0.01
for this controlled synthetic dataset. That bound is not an accuracy guarantee
for other workloads.

## Portable exports and external master state

`loss.onnx` and `gradient.onnx` retain the local function. `gradient.inlined.onnx`
and `gradient.optimized.onnx` contain only standard-domain nodes and no local
functions, so execution needs no onnax plugin or custom runtime kernel. They
still need a runtime implementing the BF16 operators. Every graph passes full
ONNX checker; function, inlined and optimized graphs are compared after loading
with dynamic batch sizes 1, 7 and 128.

ONNXScript optimizes a copy. Constant-fold size limits are set to zero for this
experiment so frozen FP32 master initializers stay byte-identical, rather than
being replaced by BF16 compute copies. Other simplification/CSE rewrites still
run. Original source and base artifacts are checked unchanged. ORT graph
optimization is not used.

The versioned `interface.json` records parameter-to-gradient names, shapes,
master/gradient dtypes, loss reduction, frozen master hashes and the derivative
convention. `adapter.npz` contains FP32 A/B masters. `checkpoint.npz` additionally
stores the Adam step and FP32 first/second moments; loading it reproduces the
next parameter/state update exactly. This is external example serialization,
not a core checkpoint API. Compute copies are regenerated from the masters.

## Measurement scope and remaining work

Separate worker processes measure the exported BF16 and FP32 graphs on the same
CPU ReferenceEvaluator backend. Each runs 10 warmups and 100 measured gradient
and external Adam updates, reporting model load/session creation, median/P95
stages, process RSS, versions and thread environment. The parent pins common
BLAS/OpenMP thread environment variables to one before worker imports. CPU calls
are synchronous; feed/output handling and reference casts are included.

These are concrete exported-graph measurements, not an experiment isolating
only dtype: the example's rank-two local VJP and the builtin general FP32 VJP
also produce different graph structure, recorded as node counts. Peak RSS
includes imports, allocator and runtime state; it does not establish BF16
activation-memory savings. No native BF16/GPU acceleration is claimed. The
[recorded report](https://github.com/justinchuby/onnax/blob/main/examples/measurements/bf16-lora-apple-arm64.json)
contains the accuracy and timing results.

Remaining P3 work includes native backend execution and device bindings,
backend-specific arithmetic/error validation, broader autocast/operator coverage,
and measurement of device memory and transfers. Generic BF16 differentiation and
device-resident training remain incomplete.

The graph uses the standard [ONNX Cast](https://onnx.ai/onnx/operators/onnx__Cast.html)
and [MatMul](https://onnx.ai/onnx/operators/onnx__MatMul.html) operators; backend
availability must still be established by execution.
